## 0. 60 秒开场

我做的是一个 AI 心理健康助手，后端 Spring Boot 3 + MySQL + Redis，AI 能力接的 DeepSeek，前端 Vue 3。

项目里技术含量集中在三块：

**第一，认证**：JWT 无状态 + Redis 黑名单做登出，这里我把 Redis 当**防线**用，走 fail-closed。

**第二，AI 对话**：SSE 流式输出 + Redis 维护上下文滑动窗口，Redis 在这里是**加速器**，走 fail-open。

**第三，Function Calling**：让模型能直接读写真实的情绪日记数据。做到一半我发现"模型的行为是概率性的"，所以把关键决策从模型手里收回了服务端。

有意思的是，**同一个 Redis，在这两个模块里承担了完全相反的角色**。我把这个对比当成整个项目最想讲的一件事。

# 模块一 · 认证：JWT + Redis 黑名单

## 1.1 链路长什么样

```
登录  → 签发 JWT（HS256，24h）→ 返回前端，前端存 localStorage
请求  → 带 token → JwtAuthenticationFilter
         ① 验签 + 验过期
         ② 查 Redis 黑名单 ── 命中 → 401，直接 return
         ③ 查用户状态（是否被禁用）
         ④ 组装 LoginUser 对象塞进 SecurityContext
登出  → 把 token 的 sha256 摘要写进 Redis，TTL = token 剩余寿命
```

关键代码：

- `filter/JwtAuthticationFilter.java` —— 过滤链，四步校验
- `service/TokenBlacklistService.java` —— 黑名单读写
- `security/LoginUser.java` —— 放进 SecurityContext 的 principal

## 1.2 【讲什么】为什么 JWT 还要配 Redis？

这是我被问得最多的问题，也是我自己做的时候纠结最久的地方。

**JWT 的价值是无状态：服务端不存 session，验签就能确认身份，天然适合水平扩展。**
**但它有个硬伤：签发出去就收不回来了。** 用户点登出，token 还在有效期内，谁拿着谁就能用 —— 这在"用户被盗号了想立刻踢下线"的场景里是致命的。

所以我的做法是：**保留 JWT 的无状态，只对"要作废的那部分 token"加状态。**
黑名单里存的不是全量 token，而是**被主动登出的那些**。没登出的用户，请求路径上只需要一次 Redis 的存在性查询，不产生任何写入。这是"无状态为主、有状态兜底"的折中。

## 1.3 【展开】黑名单的三个设计细节

**① 为什么存 sha256 摘要，不存原 token？**

三个原因。第一，**token 本身就是凭据**，原样存进 Redis，等于把凭据多复制了一份到另一个地方，一旦 Redis 被 dump 出来就是二次泄露；存摘要，即使泄露也无法反推出可用 token。
第二，**定长**。JWT 长度随 payload 变化，摘要永远 64 个字符，key 长度可控。
第三，key 是 `jwt:blacklist:<sha256>` 这种格式，**结构干净**，不会有特殊字符带来的转义问题。

**② TTL 为什么设成"token 剩余寿命"，而不是固定值？**

**黑名单只需要活到"这个 token 自然过期"为止。**
token 一旦过了 exp，验签阶段就会失败，压根走不到查黑名单那一步。这时候黑名单条目就是纯垃圾。
所以我算了一次 `token.exp - now` 当 TTL，**让黑名单和 token 同生共死** —— 不需要任何定时清理任务，Redis 自己就把空间回收了。

这里还踩过一个坑：`SET EX` 不接受 0 或负数。用户如果把一个已经过期的 token 拿来登出，剩余时间是负的，会直接抛异常。所以我加了个判断：剩余时间 <= 0 就直接 return，不入库 —— 反正它本来就无效了。

**③ 登出后的 token 还能用吗？**

不能。再拿它请求，过滤器第 ② 步就命中黑名单，返回 401 并清空 SecurityContext。

而且我返回的是一个**自定义错误码**（`TOKEN_BLOCKED`），不是笼统的 401 —— 前端能区分"你没登录"和"你的 token 已被作废"，前者跳登录页，后者可以弹一个"你已在其他设备登出"。

## 1.4 ★ 核心亮点：同一个 Redis，两种策略

这是整个项目**最值得讲的一段**，建议背下来：

项目里 Redis 用在两个地方，但**我对它们的"信任级别"是完全相反的**。

| | Redis 黑名单 | Redis 对话缓存 |
|---|---|---|
| 角色 | **防线**（security guard） | **加速器**（performance） |
| 挂了怎么办 | **fail-closed：拒绝服务** | **fail-open：降级查库** |
| 为什么 | 黑名单查不到，就等于"我不知道这个 token 是否已作废"。放行 = 一个被盗的 token 可以畅通无阻。**安全问题上，未知必须当作危险。** | 缓存查不到，MySQL 里还有真相。降级查库只是慢一点，功能完整。**性能问题上，未知只能算慢，不能算错。** |
| 代码表现 | `isBlacklisted()` 直接调 Redis，**没有 try-catch**，Redis 挂了就抛异常 | `load()` / `append()` 全部包 try-catch，失败只打 warn 日志，继续走 MySQL |
| 一致性要求 | 强一致 —— 登出必须立刻生效 | 最终一致 —— 最多读到 30 分钟前的窗口 |

**一句话总结：同一个技术组件，放在不同的业务位置上，正确的失败策略可能是完全相反的。判断依据不是"Redis 重不重要"，而是"这个数据消失之后，我是该停下，还是该退一步继续走"。**

**【追问】那 Redis 挂掉，用户就完全登不上了？**

是的，这是 fail-closed 的**有意代价**。
认证服务进不去，全站不可用。这是安全性和可用性的经典取舍 —— 我选了安全。
生产环境里如果要缓解，我的思路是 Redis 用主从 + 哨兵保证可用性，而不是靠"降级放行"来换可用 —— **靠降级换来的可用，本身就是漏洞**。

## 1.5 【追问】其他高频问题

**【追问】为什么把整个 `LoginUser` 对象放进 principal，而不是只存 userId？**

一开始我确实只放了 userId，后来发现**每个需要用户信息的地方都得再查一次库**，而且随着功能变多，到处都在重复这个动作。
改成放一个包含 `userId / username / roleType` 的小对象之后，一次性解决了"以后任何地方需要当前用户"的需求 —— 而且 `roleType` 直接用来生成 Spring Security 的 `ROLE_x` 权限，方法级注解 `@PreAuthorize` 就能用了。
我还包了一个 `SecurityUtil.getLoginUser()`，业务代码拿用户信息就是一行，不用碰 SecurityContext 的 API。

**【追问】`LoginUser` 的字段全是 `final`、只有 getter，为什么？**

它代表的是**某一次请求的身份快照**，请求处理过程中不应该被改。
不可变对象天然线程安全，也避免了"某个 Service 顺手把它改了、后面的代码拿到脏身份"这种很难查的问题。

**【追问】为什么用过滤器而不是拦截器（Interceptor）？**

因为认证要发生在**尽可能靠前**的位置。过滤器在 Servlet 层，拦截器在 Spring MVC 层 —— 用过滤器意味着未认证的请求**根本进不了 MVC 的 DispatcherServlet**，省掉了一整套参数解析、HandlerMapping 的开销。
而且 Spring Security 的过滤链本身就是过滤器体系，`addFilterBefore(...)` 挂进去，能和 `authorizeHttpRequests` 的规则天然协作。

**【追问】为什么禁用 CSRF？**

CSRF 攻击的前提是**浏览器会自动携带凭据**（比如 Cookie）。
我用的是 `Authorization` 头里的 JWT，**浏览器不会自动带**，攻击者的页面拿不到这个头，CSRF 无从下手。
加上我用的是 `SessionCreationPolicy.STATELESS`，压根没有 session 可以被利用，所以关掉是安全的。

**【追问】前端把 token 存 localStorage，不怕 XSS 吗？**

怕，这是这套方案的已知弱点。localStorage 里的东西同源的 JS 都能读到，一旦有 XSS 就全丢了。
更稳的是 `HttpOnly + Secure + SameSite` 的 Cookie，那样 JS 读不到，但代价是要处理 CSRF 和跨域 Cookie，复杂度上一个台阶。
这个项目里我选 localStorage 是因为前端是本地起的 Vue，同源问题简单。**如果上线我会换成 HttpOnly Cookie**，这一点我很清楚。

## 1.6 【追问】"你的 token 黑名单会不会撑爆 Redis？"

不会，因为**黑名单的规模天然有界**：

上限 = 单位时间内登出的用户数 × 剩余有效期。
而 token 有效期是 24 小时 —— 也就是说，**任何一个条目最多活 24 小时就会被 Redis 自动回收**，不会无限增长。极端情况下（比如被刷登出接口）会有一个峰值，但那是 24 小时的滑动窗口，不是永久堆积。

真要再省，可以把 TTL 调短（比如把 JWT 有效期砍到 2 小时 + refresh token），黑名单占用就线性下降。

# 模块二 · AI 对话：SSE 流式 + Redis 滑动窗口

## 2.1 【讲什么】为什么用 SSE，不用 WebSocket？

我的场景是**单向的**：用户发一句话，服务端把模型的回复一个字一个字推回来。不需要客户端在同一个连接上持续双向通信。

**SSE 是基于 HTTP 的单向推送，协议极简**（就是 `text/event-stream` + `data:` 行），浏览器原生支持自动重连，我用 `Flux<ServerSentEvent<String>>` 直接就能返回。
**WebSocket 是双向全双工**，能力过剩，而且要自己管连接生命周期、心跳、断线重连，还得处理网关对 Upgrade 请求的支持问题。

**一句话：能力刚好覆盖需求的技术，就是最好的技术。** 我只需要服务端推，就不该引入双向协议。

**【追问】SSE 有什么坑？**

两个，我都踩了。

**第一，SSE 的判定发生在"返回值处理阶段"，不是你手动设置响应头就能决定的。**
我一开始在 Controller 里往 `HttpServletResponse` 手动 `setContentType("text/event-stream")`，结果没用 —— 实测直接退化成把整个字符串一次性拼出来输出，完全没有流式效果。
正确做法是在 `@PostMapping` 上声明 `produces = MediaType.TEXT_EVENT_STREAM_VALUE`，让 Spring 的内容协商（content negotiation）来决定返回值怎么序列化。
**这个坑让我理解了：Spring MVC 的返回值处理链里，`produces` 的优先级高于我在代码里塞的头。**

**第二，参数校验必须发生在推流开始之前。**
`@Valid @RequestBody` 的校验在进入方法体之前完成 —— 这一点对 SSE 特别关键：**一旦开始推流，HTTP 状态码和响应头就已经发出去了，之后再出错只能表现为"流突然断了"，没法回头返回 400。**
所以把校验卡在 `@Valid` 这个时机，用户发空消息会收到一个干净的 400 + 错误 JSON，而不是莫名其妙的断流。

**【追问】为什么是 POST 不是 GET？浏览器 EventSource 只能发 GET 啊。**

对，原生 `EventSource` 只支持 GET，也就没法带请求体。
但我没有用 `EventSource` —— 我用的是 **`fetch` + `ReadableStream` 手动解析流**。这样就绕开了 GET 限制：既能把消息放在请求体里（不用 URL 编码），又能带上 `Authorization` 头（`EventSource` 连自定义头都加不了，token 只能挂 URL 上，那更糟）。
代价是要自己按 `\n\n` 切帧、解析 `data:` 前缀 —— 这点代码换来了消息不进 URL、能带鉴权头，值得。

## 2.2 ★ 核心故事：SSE 流完了却报 network error

**这个 bug 我查了很久，是我整个项目里最有收获的一次排查。**

**【现象】**

前端流的**内容完全正确**，AI 的回复一个字不少地拼出来了。但浏览器控制台每次都在最后报一个 `network error`，`fetch` 的 Promise 直接进 reject 分支。

更迷惑的是：**响应头是 200，`Content-Type: text/event-stream` 也对，`Transfer-Encoding: chunked` 也对**。从抓包看，一切正常。

**【排查过程】**

第一步，我先怀疑是后端提前关流。写了个 Node 探针（现在叫 `tools/chat-probe.js`）直接打接口，把每一个 chunk 都打出来看 —— 结果 chunk 完整，`data:` 帧和 `event:done` 都发全了，**没有异常关闭**。

第二步，既然流是干净的，那问题就在"流结束之后"的那段处理里。这时候我想起来：**SSE 在这个项目里走的是 Servlet 异步派发（async dispatch）**。

模型推流是异步的，请求的第一个线程早就还给容器了，流结束时的收尾工作是在**另一个线程**上、以一次新的 dispatch 形式完成的。

**【根因】**

我用的 Spring Security 过滤器（`SecurityContextHolderFilter`）有个特性：**它不会自动把 SecurityContext 保存到请求属性里让它跨 dispatch 存活**（它不像旧的 `SecurityContextPersistenceFilter` 那样做持久化）。

所以在异步派发那一次，**SecurityContext 是空的**。Spring Security 的 `AuthorizationFilter` 在派发阶段重新跑一遍授权检查，拿不到认证信息 → 判定未授权 → 在响应已经提交、流已经写完的情况下抛异常 → 连接被异常中断 → 浏览器看到 `network error`。

**这解释了那个诡异的现象：内容是对的（第一次 dispatch 正常推完了），但连接是被异常掐断的（第二次 dispatch 炸了）。**

**【修复】**

在过滤器里，把 SecurityContext 显式存进一个**基于请求属性的仓库**：

```java
private final SecurityContextRepository securityContextRepository
        = new RequestAttributeSecurityContextRepository();

// 认证通过之后：
SecurityContext context = SecurityContextHolder.getContext();
context.setAuthentication(authcation);
SecurityContextHolder.setContext(context);
securityContextRepository.saveContext(context, request, response);
```

请求属性的生命周期覆盖整次请求（包括异步派发），所以第二次 dispatch 能重新读到身份，授权检查通过，流正常收尾。

**【为什么值得讲】**

这个 bug 的价值在于：**它教我不能只看"内容对不对"，要看"连接的结束方式对不对"。**
内容全对但连接异常关闭，说明问题不在业务逻辑，而在请求的生命周期管理上。
而一旦理解了"Servlet 异步派发 = 一次请求被处理了两遍"，Spring Security 上下文为什么会在第二遍丢失，就是自然而然的事了。

## 2.3 【讲什么】Redis 滑动窗口：为什么需要它

大模型是**无状态**的 —— 它不记得上一句。要做多轮对话，就得每轮把历史消息一起发给它。

如果每轮都去 MySQL 捞全部历史：

- **慢**：每句话之前都先来一次数据库查询，而且历史越长查得越久；
- **浪费**：模型有上下文长度上限，我根本不可能把 1000 轮对话全发过去，发过去的也只是最后几十条。

所以我在 MySQL 前面加了一层 Redis，**按"只有最近 N 条才有意义"这个业务事实，把窗口固化在缓存里**。

## 2.4 【展开】滑动窗口怎么实现的

```java
// 读：取最近 20 条
List<String> raw = listOps.range(key, -MAX_MESSAGES, -1);

// 写：追加两条（用户 + AI），裁到 20 条，续期 30 分钟
listOps.rightPushAll(key, userJson, assistantJson);
listOps.trim(key, -MAX_MESSAGES, -1);   // ← 只留最近 20 条
redis.expire(key, TTL);                 // ← 每次写入刷新 TTL
```

- key 结构：`chat:history:{sessionId}`
- 窗口大小：**20 条消息 = 10 轮对话**
- TTL：**30 分钟**

**【展开】为什么要用 Redis 的 List，而不是 String / Hash？**

因为 List 天然匹配"**只有尾部才重要**"这个语义。

- `RPUSH` 追加是 O(1)；
- `LTRIM key -20 -1` 一句话就完成了"裁剪到最近 20 条"，不需要我自己算索引、不需要读出来再写回去；
- `LRANGE key -20 -1` 直接按范围取尾部，负索引从右边数，**语义和"最近 N 条"完全重合**。

如果我用 String 存一个大 JSON：每次追加都要 `GET` 出来 → 反序列化 → 添加 → 序列化 → `SET` 回去，**一次追加 = 一次全量读写**，对话越长这个操作越贵，而且还不是原子的。
如果用 Hash：得自己维护下标，还得额外处理"淘汰最老的"，把本该由 Redis 承担的逻辑搬到了应用层。

**选数据结构的时候，我优先找"语义上最贴合业务动作"的那个，而不是存储上最省事的那个。**

**【展开】20 条是怎么裁的？为什么不裁得更大？**

这里我做过一次明确的取舍，结论是**保持 20 条不动**，理由有两个：

**第一，这是成本和质量的正面对冲。** 上下文越长，token 消耗越大、响应越慢、越贵。而这个项目跑的是我自己的 API Key。

**第二，也是最关键的：盲目扩大窗口反而会降低回答质量。**
窗口是"最近 N 条"，不是"相关 N 条"。用户如果中途**换了话题**，窗口里就混进了一大堆跟当前话题无关的历史 —— 这些内容会稀释模型的注意力，同时白烧 token。
而如果用户是在**持续聊同一件事**，那最近 10 轮本身就都是围绕这个主题的，话题主体性不会丢，最多丢一些细节。

**所以"窗口大小"不是一个纯技术参数，它取决于产品形态。** 如果这是个客服机器人（话题连续、需要精确引用早期信息），我会调大甚至上向量检索；但这是个陪聊产品，10 轮是合理的。

**【展开】TTL 30 分钟和滑动窗口是什么关系？**

这俩是**两个不同维度**的过期：

- **窗口（20 条）是空间维度的过期**：消息多了，老的被挤出去。
- **TTL（30 分钟）是时间维度的过期**：用户 30 分钟不说话，说明这次会话基本结束了，整个 key 直接消失，把内存还给 Redis。

而且我每次写入都会 `expire` 续期 —— 用户连续聊两小时，缓存不会在第 30 分钟突然蒸发，因为每轮都在续。**只有"真的 30 分钟没动静"才会过期。**

## 2.5 【展开】缓存和 MySQL 怎么配合

用的是 **Cache-Aside（旁路缓存）**：

- **读**：先查 Redis → 命中直接返回 → 未命中回源 MySQL → **顺手回填 Redis**
- **写**：先写 MySQL（真相）→ 再更新 Redis（缓存）

**MySQL 是唯一真相源，Redis 只是一份可丢弃的副本。**
判断依据很简单：**Redis 里所有的数据都能从 MySQL 重新算出来，那就说明它只是缓存。**

具体在对话流程里：

- `AIService.chat()` 里 `chatMemoryService.load(sessionId)` 拿上下文
- 流式响应**正常结束**之后，`saveRound()` 一次性把这一轮（用户 + AI）落库：**先写 MySQL，再写 Redis**
- 删除会话时 `evict()` 把缓存一起清掉

**【追问】为什么是"流结束后一起存"，而不是"用户发的时候先存用户消息"？**

因为我希望**一轮对话要么都在，要么都不在**。

如果用户消息先存、AI 回复后存，中间一旦失败（模型超时、连接断了），数据库里就留下一个"只有提问没有回答"的半截记录。下次读出来拼进 prompt，模型会看到一个悬空的问题，上下文语义就乱了。
一起存，一轮就是一个原子单元。

**代价我也很清楚**：如果流中途断了，这一轮就彻底丢了 —— 我在测试里真的遇到过（DeepSeek 那边 `Connection reset`），结果是用户消息都没落库，对话记忆里直接留了个洞。**这是我已知的缺陷，如果要做健壮版本，我会在流开始时就存用户消息、流失败时把它标记成"未完成"而不是直接丢弃。**

**【追问】缓存和数据库会不会不一致？**

会，而且我选的是**"接受短暂不一致"**这条路，因为对话缓存对一致性要求很低。

最坏情况：用户在两台设备上同时聊同一个会话，A 的消息落库了但 B 的缓存还是旧的 —— 那 B 这轮少看到 A 的一句话。**30 分钟后 TTL 过期，或者换一个会话再回来，就自愈了。**

这里我的判断是：**不是所有不一致都值得修。** 对话上下文的"最新一条没看到"，对体验的影响远小于修复它要付出的复杂度（分布式锁 / 版本号 / 消息队列）。
但如果换成**订单金额**这种数据，我就会用完全不同的方案。

**【追问】多实例部署，这套缓存有问题吗？**

没有，因为**缓存 key 本身是共享的**（`chat:history:{sessionId}`），所有实例读的是同一个 Redis。

真正要注意的是**并发写同一个会话**：两个实例同时追加，可能发生读-改-写的丢失更新。
但实际上这里比看起来安全 —— `RPUSH` 和 `LTRIM` 都是 Redis 的**原子命令**，追加本身不会互相覆盖。风险主要在"回填缓存"那条路径（先查库再回填），有极小的窗口可能回填进稍旧的数据。加上 TTL 兜底，我认为对这个场景可以接受。

## 2.6 【追问】SSE 长连接会不会把线程占满？

**这正是流式接口必须异步的原因。**

如果同步阻塞：一个请求占一个 Tomcat 线程，等模型吐完才释放。100 个用户同时聊天 = 100 个线程挂着，Tomcat 默认 200 个线程池很快见底。

我返回的是 `Flux<ServerSentEvent<String>>`，**Reactor 的响应式流**：

- 整个链路是**非阻塞**的，模型每吐一个 token 就触发一次事件推给客户端；
- 等待模型生成的那段时间，**不占用任何 Tomcat 线程**；
- 线程还给容器去处理别的请求。

这也是我前面踩的"异步派发 SecurityContext 丢失"那个 bug 的来源 —— **异步给我省了线程，但代价是请求的生命周期变得复杂了。**

# 模块三 · Function Calling：让 AI 读写真实业务数据

## 3.1 【讲什么】要解决什么问题

普通聊天机器人只能"说"，不能"做"。用户说"帮我把今天的感受记下来"，它只会回一句"好的我记住了"——**其实什么都没记**。

Function Calling 就是让模型能**调用我后端的真实方法**：用户说"帮我记一下今天的感受"，模型自己判断该调 `createDiary`，自己从对话里抽出情绪评分、主要情绪、正文，然后我的服务端真的往数据库写一条。

我把三个能力封装成了工具：

- **写情绪日记**（`createDiary`）
- **按日期范围查**（`queryEmotionTrend`，参数是 `startDate` / `endDate`）
- **查最近 N 天**（`queryRecentEmotion`，参数就一个 `days`）

用户问"我这周心情怎么样"，模型会调查询工具拿真实数据来回答，而不是瞎编。

**为什么要有两个查询工具**：一开始只有按日期范围的那个，模型得自己把"最近""这几天"换算成日期 —— 算"这周"没问题，算"上个月""上上周末"就开始出错。所以我又加了一个"最近 N 天"，**让它只需要回答"多少天"这个它擅长的数字，日期换算交回服务端。**（这跟下面"模型没有时钟"那个坑是同一个思路，见 3.3 坑 1）

实现要点：

- 用 `ChatClient`（不是裸的 `ChatModel`），因为它会自动处理 **"模型要求调工具 → 执行工具 → 把结果回灌给模型 → 再生成回答"** 这个循环
- `chatClient.prompt().messages(messages).tools(tools).stream().content()`
- 流式输出保持原样，工具调用对前端透明

## 3.2 ★ 三个核心设计决策

### 决策一：userId 靠构造注入，绝不作为工具参数

```java
// 每个请求 new 一个工具实例，把当前用户注入进去
DiaryTools tools = new DiaryTools(emotionDiaryService, emotionDiaryMapper, userId);
```

**工具的入参是模型生成的，属于不可信输入。**

如果我把 `userId` 做成工具参数，模型只要被诱导（或者单纯自己猜错）传一个别人的 ID，就能往别人的日记里写数据 —— 这是一个**由模型幻觉触发的越权漏洞**。

所以身份信息**从服务端的登录态注入**，模型看不见、也碰不到。工具里所有的数据库操作，`userId` 都是外部传进来的常量，模型能影响的只有"写什么内容"，不能影响"写到谁那儿"。

我还专门写了验证：用 A 账号问"我这周心情怎么样"，确认它**查不到 B 账号的日记**。

**【追问】为什么每个请求 new 一个工具实例，不注册成单例 Bean？**

因为 `userId` 是**每个请求不同**的。
注册成单例的话，`userId` 要么得做成方法参数（违反上面那条），要么就得用 ThreadLocal 传 —— 而 Reactor 的流式链路会在多个线程间切换，ThreadLocal 根本不可靠。
**每个请求 new 一个实例，天然线程安全，没有共享状态。** 代价是每轮对话多几个对象分配，可以忽略。

原则是：**把"随请求变化的状态"放在实例里，而不是放在参数里或全局里。**

### 决策二：能用代码保证的，不要交给模型判断

这条是做完这个模块最大的收获。

一开始我的日记写入是"覆盖"语义（复用表单的 `save`）。测试时发现一个要命的问题：

**用户早上记了一笔"今天好倒霉"，下午又说"下午好多了"——早上的内容会不会丢？**

我写了个探针 `tools/fc-overwrite-probe.js` 跑了 6 轮去测，结果是：

| 场景 | 结果 |
|---|---|
| 早上下午在**同一个会话** | 3/3 模型主动把两段合并保住了 |
| 下午**另起新会话**（中午关了页面） | **3/3 早上的内容被抹掉** |

**同一份代码，同样的操作，结果取决于用户中午有没有关页面。**

根因很清楚：**模型只能看到对话历史，看不到数据库。** 同一个会话时，早上那轮还在上下文窗口里，模型手里有原文，它就自己拼上了；一旦换了会话，历史里没有早上那段，模型只把下午那句发过来，服务端一覆盖，早上就没了。

所以我的修法是：**把"合并"这个决策从模型手里收回服务端。**
模型只负责回答"用户这次说了什么"（提取内容、判断情绪），**"这段内容和已有的怎么合"由代码确定性保证**：

```java
if (existingText.contains(incoming))  return existingText;   // 已经有了，不动
if (incoming.contains(existingPlain)) return incoming;      // 模型带了全文，直接用
return existingText + "\n" + stamp(incoming);               // 正常追加
```

**一句话总结：模型负责"理解"，代码负责"决策"。凡是判错会丢数据的地方，都不能交给概率性的东西去决定。**

**【追问】追加和覆盖，你到底怎么选的？**

追加（APPEND）：保留已有内容，把这次说的接在后面，带上 `【HH:mm】` 时间戳。
覆盖（REPLACE）：把整篇换掉。

我**只实现了追加，故意没给模型重写权限**。理由是**代价不对称**：

| | 模型判错的后果 |
|---|---|
| 追加判成重写 | **前面的内容没了，不可逆** |
| 重写判成追加 | 内容多了几句，用户看一眼就能改 |

一个是丢数据，一个是脏数据。凡是对"判错就不可逆"的能力，都不该交给一个概率性的组件。
而且**编辑能力前端表单已经有了** —— 用户真想把日记改掉，打开表单直接编辑，那里能看到全文，比在对话框里说"帮我改掉早上那句"可靠得多。FC 的定位是"聊天时随手记一笔"，不是"编辑器"。

这就是**最小权限原则**：不给模型它不该有的破坏性能力。

### 决策三：只写用户表达过的，不推断、不补全

日记有七个字段，但模型不可能全知道。我的规则是：

**只写用户明确表达过的，没提到的字段保持 `null`，绝不根据语气推测。**

举例区分：

- 用户说"今天好累" → 模型判断"疲惫"，打分 5 分 → **这是理解**，用户表达了情绪本身，模型把它映射到刻度上，这是它最擅长的事，可以做。
- 用户**没提**昨晚睡得怎么样 → 睡眠质量留 `null` → **如果模型从"累"反推"睡眠质量=2"，那就是编造**，不能做。

我实测验证过：只发"帮我记一下，今天还行，就是有点累"，结果 `sleep_quality` / `stress_level` / `emotion_triggers` **三个字段都是 null**，没有瞎编。

**产品上的好处**：有些用户就是懒，只想打个卡记录心情、不写原因。这时候不该逼他填，留空就好 —— 这个字段的"未填写"状态，**在数据模型里就是 `null`，不需要任何额外的设计**（表里除了 `mood_score`，其余字段本来都是 nullable）。

## 3.3 踩坑实录

### 坑 1：模型没有时钟

**【现象】** 今天是 2026-10-01，用户问"我这周心情怎么样"，模型回答：

> 我查了一下，这周（**6月9日到6月15日**）暂时还没有找到情绪记录。

一个凭空捏造的日期区间，查了个空，然后告诉用户"你没有记录"——数据明明在库里。

**【根因】** 工具签名是 `queryEmotionTrend(startDate, endDate)`，用户说的是"这周"，**这个换算得模型自己做**。但我的系统提示词里从头到尾**没告诉它今天几号**。它只能从训练语料里蒙一个日期。

**所有相对时间（今天 / 这周 / 最近 / 上周）在 LLM 眼里都是没有锚点的词。**

**【修复】** 提示词改成模板，每轮把当天日期 + 星期拼进去：

```java
private static final String SYSTEM_PROMPT_TEMPLATE = """
    ...
    今天是 %s。
    ...
    当用户说"今天""这周""最近"时，都是相对于上面那个日期。
    请先把它们换算成 yyyy-MM-dd 再传给工具，不要自己猜一个日期范围。
    """;
```

修完立刻正常，模型自己算出了 `2026-09-28 到 2026-10-01`。

**【为什么值得讲】** 这不是"模型笨"，是**我们没给它上下文**。看起来像 AI 不听话的问题，往深查往往是"信息没给到"。

### 坑 2：字符串 "null" 和数字 0 —— 同一个意图的两种脏值

**【现象】** 我在工具参数描述里写"没提到就传 null"，结果模型把**字面量字符串 `"null"`** 传了进来。
在 SQL 日志里抓到的现场：

```
INSERT INTO emotion_diary (..., emotion_triggers, ...) VALUES (..., null(String), ...)
                                                             ^^^^^^^^^^^^ 字符串
```

`emotion_triggers` 是 `String` 类型，这四个字母原样落库了。

当时我判断"`sleep_quality` / `stress_level` 是 `Integer`，字符串塞不进去，模型只能省略 —— **它们反而逃过一劫**"。
**这个判断后来被证明是错的** —— `Integer` 那两个参数不是逃过一劫，而是踩了一个更深的坑：Spring AI 在转换时会直接抛异常，**工具一次都执行不了**。详见下面【坑 6】。
**同一个 `"null"`，两个参数类型，两种完全不同的炸法。**

**【修复一】** 在工具层做归一化，把 `"null" / "none" / "undefined" / "n/a" / 空串` 全部转成真 `null`：

```java
private static String blankToNull(String v) { ... }
```

同时把提示词从"没提到就传 null"改成"没提到就**省略这个参数**"—— 措辞本身也在诱发这个行为。

**【现象二】** 堵了字符串之后，模型**改用 `0` 表示"没填"**。`Integer` 参数传不了字符串，它就退而求其次传了个越界数字，睡眠质量 0 分照样落库。

**【修复二】** 量表值做范围校验，越界当没填：

```java
private static Integer scoreOrNull(Integer v, int min, int max) {
    return (v == null || v < min || v > max) ? null : v;
}
```

**【为什么值得讲】**

**同一个"我不填"的意图，模型会因为参数类型不同，换两种不同的脏值表达方式。**
这类"模型输出的脏值"必须在**工具层**洗掉 —— 不能指望 Service 去认识 LLM 的怪癖。**边界的职责就是把外部世界的不规范挡在业务逻辑之外。**

### 坑 3：我加的时间戳，污染了我自己的去重

**【现象】** 我做了"同一段话不重复追加"的去重，但测试时同一句话发两遍，**还是被追加了两遍**。

**【根因】** 我存进数据库的正文长这样：`【20:52】今天早上特别倒霉……`
而做去重时我用的是 `existingText.contains(incoming)` —— 存进去的文本**多了 `【20:52】` 这个前缀**，导致 `contains` 永远匹配不上。**我自己加的时间戳，把我自己的比对逻辑搞坏了。**

**【修复】** 比对之前先把时间戳正则剥掉：

```java
private static final Pattern STAMP_PATTERN = Pattern.compile("【\\d{2}:\\d{2}】");
String existingPlain = STAMP_PATTERN.matcher(existingText).replaceAll("").trim();
```

**【为什么值得讲】** 这个坑**不写测试根本发现不了** —— 表面上功能都正常，只有重复提交这种边界场景才暴露。

### 坑 4：AI 路径绕过了 @Valid

**【现象】** DTO 上明明有 `@Min(1) @Max(10)`，但 AI 传入的越界评分照样能落库。

**【根因】** `@Valid` 只在 `@RequestBody` 那条路上生效（表单接口）。
**AI 工具是手动 `new` 出来的 DTO，压根不经过校验器。**

**【修复】** 在 Service 层补一道范围检查 —— 这样两条入口都被覆盖，而不是只在 Controller 上打补丁。

**【为什么值得讲】** **校验的层次要和"数据的来源数量"匹配。** 只有一个入口时，在入口校验就够了；一旦有了第二个入口（AI 工具、定时任务、消息队列），就必须把校验下沉到业务层。

### 坑 5：流一断，整轮丢失

**【现象】** 测试时 DeepSeek 那边 `Connection reset`，前端收到一个空的回复，**用户消息也没落库**。

**【根因】** 我把落库挂在 `doOnComplete` 上（流正常结束才存）。出错时走了 `onErrorResume` 分支，`doOnComplete` 根本不执行。
于是这一轮**在数据库里完全没有痕迹**，对话记忆里直接留了个洞 —— 用户下次回来，AI 完全不记得刚才聊过什么。

**【现状】** 这是**已知未修的缺陷**。要修的话，思路是：流开始时先把用户消息落库并标记为"进行中"，流成功结束后补上 AI 回复并改成"完成"，失败时把这条标记成"未完成"、不让它进上下文窗口。

**（主动说出未修的缺陷，比被追问出来强得多 —— 它证明你知道边界在哪。）**

### ★ 坑 6（最值得讲的一个）：不是模型幻觉，是框架的类型转换炸了

**【现象】**

用户让 AI 记一笔日记，AI 回：

> 好的，我这就帮你把这份开心也记上。**已经帮你记好了**，今天（10月2日）的日记里又添上了：今晚又吃了大蛋糕，很开心。

**但数据库里什么都没有。** 而且它是**间歇性**的 —— 有时成功、有时失败，大概五次里错四次。

**【排查第一步：看日志】**

后端日志里，那一轮**既没有 `[Tool]` 的执行记录，也没有 `emotion_diary` 的写 SQL**。

第一反应当然是"**模型幻觉了** —— 它没调工具，只是嘴上说记了"。这个判断看起来完全合理，因为它解释了所有现象。

**但这个判断是错的。**

**【排查第二步：打开 Spring AI 的 DEBUG 日志】**

```
DEBUG DefaultToolCallingManager : Executing tool call: createDiary
DEBUG MethodToolCallback        : Starting execution of tool: createDiary
ERROR MessageAggregator         : Aggregation Error

java.lang.NumberFormatException: null
  at java.math.BigDecimal.<init>(BigDecimal.java:692)
  at org.springframework.ai.util.json.JsonParser.toTypedObject(JsonParser.java:148)
  at org.springframework.ai.tool.method.MethodToolCallback.buildTypedArgument(MethodToolCallback.java:150)
```

**模型调了工具。是 Spring AI 在把参数转成 Java 类型的时候抛了异常。**

**【排查第三步：反编译那一行】**

```bash
javap -p -c -classpath spring-ai-model-1.0.1.jar org.springframework.ai.util.json.JsonParser
```

看 `toTypedObject` 对 `Integer` 的处理：

```java
if (resolvedType == Integer.class) {
    BigDecimal bigDecimal = new BigDecimal(value.toString());
    return Integer.valueOf(bigDecimal.intValueExact());
}
```

**它对这个值没有任何防护。**

**【根因】**

模型把**字符串 `"null"`** 传进了 `Integer` 类型的参数 —— 它就是用这个来表达"这个字段我没填"。

`new BigDecimal("null")` → 抛 `NumberFormatException`。

而异常发生在 `MethodToolCallback.buildTypedArgument` 里，**比我自己工具方法的第一行代码还要早** —— 所以工具一次都没执行，日志里自然什么都没有。

**【修复】**

把所有数值参数从 `Integer` / `int` 改成 `String`，自己解析：

```java
// 改前：Spring AI 会 new BigDecimal(value.toString()) —— 脏值直接炸
Integer sleepQuality,

// 改后：Spring AI 只做 value.toString()，永不抛
@ToolParam(description = "睡眠质量，1 到 5 的整数…") String sleepQuality,

// 工具内部自己洗：
dto.setSleepQuality(scoreOrNull(parseIntOrNull(sleepQuality), 1, 5));
```

`parseIntOrNull` 把 `"null"` / `""` / `"abc"` / `"2.5"` 全部归一成"没填"，越界的再丢掉。

**修复前 `NumberFormatException` 满屏；修复后 0 条，42 次工具调用全部成功。**

**【为什么这个坑最值钱】**

**1. 它是最糟的失败方式：假成功。**
不是报错、不是白屏，而是**用户以为记上了、其实什么都没有**。这种失败比崩溃危险得多 —— 崩溃至少你还会去查。

**2. 它的根因和表象隔了三层。**
表象是"模型幻觉"，第一层是"工具没执行"，第二层是"Spring AI 抛异常"，第三层才是"模型传了字符串 `"null"`"。**只看前两层，你会去改提示词 —— 那是在给一个根本没坏的东西打补丁。**

**3. 它是框架级的坑，而且是我自己上一次修复留下的。**
上一轮我已经发现"模型会把 `"null"` 当字符串传"，并且给 `String` 类型的字段加了清洗。但 `Integer` 类型的参数绕过了我的清洗 —— 因为 **Spring AI 在进入我的代码之前就抛了**。
**同一个问题，我只堵住了一半的入口，它就从另一半换了一层壳冒出来。**

**4. 它的修复过程是完整的"从日志到字节码"。**
先看日志定位到"哪个类哪一行抛的"，再 `javap` 反编译确认那一行到底在干什么。这个方法在遇到第三方库的问题时特别有效 —— **不要猜它怎么实现的，去看**。

**【一句话总结】**

**框架的隐式转换一旦不可控，就把它挪到自己能看见的地方。** 参数从 `Integer` 改成 `String` 看起来是"退步"，但它把一个我控制不了的转换，变成了我能读懂、能测试、能兜底的一段代码。

### ★ 坑 7：模型记着记着就不动手了 —— 它在学历史里的自己

**【现象】**

用户在**同一个会话里连续记了几笔之后**，AI 回"已经帮你记好啦～"，但数据库里什么都没有。
而且是**越记越容易失灵**：第一笔好好的，第三、四笔开始就空转了。

**【证据】**

- 后端日志里那一轮**既没有 `[Tool]` 记录，也没有 `emotion_diary` 的写 SQL**
- 日记的 `updated_at` 停在好几次记录之前，压根没被碰过

**【根因：模型在模仿它自己】**

把会话历史拉出来，一眼就明白了：

```
用户 | 帮我记录一下，今晚吃了大蛋糕很开心
AI   | 好呀…已经帮你记好啦～ 🎂
用户 | 帮我记录一下，我吃了很多烧烤，很满足
AI   | 好呀…已经帮你记好啦～ 🍢
用户 | 帮我记录一下，我又吃了很多宵夜，很满足
AI   | 好呀…已经帮你记好啦～ 🍜
```

再往深一层看，是**我的设计漏了一样东西**：

> **我保存对话时只存了模型的最终回复 —— 工具调用的过程（tool_call + 工具结果）压根没进历史。**

所以模型看到的历史里，"记录成功"这件事**从来不需要调用工具，说一句就行**。
它照着这个示范往下学，几轮之后就开始只动嘴不动手。

**这不是模型"变懒"了，是我给它的历史里，正确的做法从来没出现过。**

**【三个失败的修法，和一个危险的回退】**

**① 提示词加硬规则 —— 无效。**
在系统提示词最顶部加了一段"★★ 最重要的一条：必须真的调用工具；历史里那些'已经记好了'是当时的回复，不代表这次也能这么说"。**中毒的会话依旧 0/3。**

**② 提示词加正确示范 + 自检 —— 还是无效。**
又把完整流程写进去（"用户说要记录 → 你先调 createDiary → 拿到『已记录：…』→ 才回复"），还加了一句"写回复前先自检：这轮我拿到工具返回了吗"。**依旧 0/3。**

**③ `tool_choice = "required"` 强制调用 —— 看起来最对症，结果踩了大坑。**

DeepSeek 的 options 里确实有 `setToolChoice`，我一度以为找到正解了。跑起来才发现：

> **工具被无限循环调用，每 2 秒写一次数据库，停不下来。**

原因是 Spring AI 的自动工具执行本身是个循环（模型 → 执行工具 → 结果回灌 → 模型再来一轮…），
而 `tool_choice=required` **在循环的每一轮都生效** —— 模型被强制不停地调工具，永远出不来。

（还好我的写入有去重，数据没被写坏；但这个改动必须立刻回退。）

**教训：想强制模型使用某个能力，必须先想清楚"这个强制会不会在框架的自动循环里反复生效"。**

**【最终修法：让工具调用在历史里留下证据】**

既然模型看不到"记录 = 调工具"这个因果，那就**把它写进历史**：

每轮真正调用过工具时，在**存给模型看的那份回复**后面附上痕迹：

```
〔本轮实际执行了工具：createDiary（写入成功，日期=2026-10-02）〕
```

三个必须注意的细节：

1. **MySQL 和 Redis 要存同一份**（都带痕迹）—— 否则缓存命中和未命中会看到两种历史；
2. **前端拿到的要自动剥掉** —— `listAll`（详情页）和 `preview`（列表页预览）都先剥再返回；
3. **痕迹里千万不要塞日记正文** —— 我第一版把整篇正文都带进去了，历史里每轮一份越来越长的快照，反而把模型搞得更晕。

**【效果与残留】**

| | 修之前 | 修之后 |
|---|---|---|
| 同一个会话连续记录 6 轮的成功率 | 2/5 | **5/6** |

**明显改善，但残留 1/6 会失灵。**

这是我的诚实结论：**这是模型的行为特性，不是我能用代码完全消除的。**
我能做的是把它从"经常坏"改善到"偶尔坏"，并把这个限制写进已知问题 —— 而不是假装它不存在。

**不是所有问题都能"修好"，有些只能"改善到可接受"。能分清这两者，也是工程判断的一部分。**

### 【番外】同一个坑里，我的调试工具骗了我三次

上面那两个 bug，我一度都得出过**完全错误的结论**（"80% 幻觉""0/10"），还差点去改一个根本没坏的东西。
原因是**我的探针写错了三次**：

**第一次错的探针：测试数据改变了被测行为。**
我在消息里塞了个随机数字当标记（`帮我记一下：长会话标记197130`），方便程序判断有没有写进去。
结果模型说："这个看起来像测试标记，你是想原样记进去吗？" —— **它主动来跟我确认，压根没调工具。**
于是真实的 bug 复现不出来。**我为了观测加的东西，改变了被观测的行为。**

**第二次错的探针：我把"去重生效"读成了"没写进去"。**
改成用"正文长度有没有变长"判断之后，我得到了 0/10 的惨烈结果。
但真相是：我的日记写入**本来就有去重**（同一段话不重复追加），而探针每次都发**同一句话** —— 第二次开始就被去重挡掉了，正文当然不变。
**那个"0/10"，恰恰说明去重工作得很好。**

**第三次错的探针：`updated_at` 只有秒级精度。**
改用 `updated_at` 判断"工具有没有执行"之后，我以为终于对了。但 `updated_at` 是 `datetime`（**秒级**），
两轮落在同一秒里，字符串完全相同 —— 我又把"执行了"读成了"没执行"。
再加上那时发的还是**固定重复的句子**（被去重挡着，正文也不变），**两个信号同时失效**，结论就全错了。

**最后改对的探针：用独一无二的词做精确比对。**
每次随机挑一个"日记里还没出现过的独特词"造一句自然的日常话，然后**只在正文里找那个词**。
判定立刻干净了 —— 结果和日志证据完全对得上。

**【教训】**

**测量工具本身也会骗人，而且它骗你的时候比 bug 更隐蔽。**
当测量结果和日志证据矛盾时（日志说工具执行了 42 次，探针说成功 0 次），**不要急着相信任何一边 —— 先去核对测量方法。**

还有一条更实际的：**我三次都是"改了探针就以为对了"，没有拿另一路证据去交叉验证。**
真正让我惊醒的是 DB 里那三条带着工具痕迹的消息 —— **日志和数据库不会跟着我的假设走，它们才是可信的那一路。**

这一点在面试里比那个 bug 本身更能说明问题：**它证明我会怀疑自己的结论，而不是只怀疑代码。**

## 3.4 【追问】Function Calling 其他高频问题

**【追问】模型怎么知道该调哪个工具？**

靠 `@Tool` 注解里的 `description`。Spring AI 会把工具名、参数名、参数说明、描述一起打包成 JSON Schema 发给模型，**模型读这些文字来决定调不调、调哪个、参数填什么**。

所以**写工具描述本质上是在写提示词**。我踩的"传字符串 null"那个坑就是描述写得不严谨导致的。

**【追问】模型一次可以调多个工具吗？**

可以，Spring AI 的 `ChatClient` 会处理多轮工具调用循环：模型返回 tool_calls → 执行 → 结果回灌 → 模型可能再要求调工具 → 再执行，直到模型给出最终文本回答。这个循环对我是透明的。

**【追问】工具执行失败了会怎样？**

我在工具内部 `try-catch` 了，**失败时不抛异常，而是返回一句错误描述给模型**：

```java
catch (Exception e) {
    log.error("[Tool] createDiary 失败", e);      // 真实原因留在服务端日志
    return "记录失败：" + e.getMessage() + "。请检查参数后重试。";
}
```

**抛异常会把整轮对话打断**，用户看到的是一个莫名其妙的断流；返回文字描述，模型可以据此修正参数重试，或者转告用户。**真实的技术细节留在服务端日志里，不往前端泄漏。**

**【追问】工具调用的结果，用户能看到吗？**

看不到。工具结果只回灌给模型，模型再组织成自然语言回复给用户。用户对"模型刚刚往数据库写了一条"这件事是无感的 —— 这是有意的，**不该让用户看到内部机制**。

**【追问】怎么防止模型乱调工具？**

两点。第一，**工具描述里明确写了触发条件**："当用户表达了'想记录''帮我记一下'这类意图时才调用"。
第二，也是更可靠的：**即使它乱调了，写入的内容也必须来自用户的原话**（参数描述里写了"保留原话，不要自己编造"）。

说实话，**光靠提示词约束模型是不可靠的**——这就是为什么我把"追加还是覆盖""写到谁那儿""分数是否合法"这些**后果不可逆的决策全都放在了服务端代码里**，而不是依赖模型听话。

# 模块四 · 知识库：Cache-Aside（简单带过）

这块的存在意义很明确：**把 Cache-Aside 真的写一遍**。文章是典型的读多写少数据，正好是缓存的最佳战场。

- 读：查缓存 → 未命中查库 → 回填缓存
- 写：**先删库，再删缓存**

**顺序为什么不能反？**
如果先删缓存、还没删库的那一瞬间来了个读请求，它会从数据库读到**"还没删掉的旧数据"并写回缓存** —— 于是缓存里留下一条数据库里已经不存在的**"幽灵文章"**，要等 TTL 过期才能自愈。
先删库再删缓存，最坏只是中间那一下脏读，最终仍然一致。

阅读数用 `read_count = read_count + 1` 在**数据库层做原子自增**，然后让缓存失效 —— 而不是 `SELECT` 出来 `+1` 再 `UPDATE`，那样并发下会丢更新。

**【追问】为什么是"删缓存"而不是"更新缓存"？**

**更新缓存要处理并发写的覆盖顺序问题**：两个请求同时更新，A 先算完但后写入，缓存里就留下了 A 的旧值。
**删除是幂等的**，谁先删谁后删结果一样，下一次读自然会从数据库加载到最新值。
而且如果这个缓存值需要复杂计算（比如聚合统计），"删掉"比"每次都算一遍再写"更省。

代价是第一次读会 miss（缓存击穿）。对我来说文章详情不是热点数据，可以接受。

# 模块五 · 契约设计：一个错误码引发的全线误伤

## 5.1 现象

**点一下"知识库"菜单，直接被踢回登录页。** 而且不是偶发 —— 每次必现。

一开始我以为是权限配置的问题（是不是这个路由不在白名单里）。但登录页的逻辑是"token 失效才跳"，而我的 token 明明还有效。

## 5.2 排查

打开浏览器 Network，一眼就看到：知识库页面在请求 `/api/knowledge/article/page`，返回**HTTP 200**，响应体是：

```
{"code":"-1","message":"文章不存在","data":null}
```

HTTP 是 200，但业务码是 `-1`。而前端 `request.js` 的响应拦截器里写着：

```js
if (data.code === '-1') {
  localStorage.removeItem('token')
  window.location.href = '/auth/login'
}
```

**找到了。前端把 `-1` 当成了"登录过期"。**

再往下追，为什么这个接口会返回"文章不存在"？因为后端**根本没有 `/page` 这个接口**，只有 `@GetMapping("/{id}")`。Spring 把路径里的 `page` 当成了文章 ID，`selectById("page")` 查不到，于是抛了业务异常。

## 5.3 根因：一个错误码承载了多种语义

再往深看一层，问题不在知识库，也不在那个拦截器，而在**错误码的设计**：

```java
// 后端：所有业务异常统一走这个
private Result<Void> fail(String message) {
    Result<Void> result = Result.error();   // ← Result.error() 的默认码就是 "-1"
    result.setMessage(message);
    return result;
}
```

所以后端返回的 `-1` 可能是"文章不存在"、可能是"密码错误"、可能是"参数校验失败"、可能是"系统繁忙"……

**而前端看到 `-1`，只能猜。它猜成了"登录过期"。**

这就是整个 bug 的本质 ——

> **一个错误码承载多种语义，调用方就只能猜；能猜错的地方早晚会错。**

而且这个错误方向特别糟：**它把"业务失败"误判成了"身份失效"**，代价不只是提示错了，而是**直接把用户的登录态清掉了**。

## 5.4 修复：让错误码自己去划分语义

后端其实**已经有**细分的认证错误码了，只是前端没用：

```java
TOKEN_INVALID("A0230", "token无效"),
TOKEN_EXPIRED("A0230", "token已过期"),
TOKEN_BLOCKED("A0230", "token已加入黑名单"),
TOKEN_ACCESS_FORBIDDEN("A0231", "token已被禁止访问"),
AUTHORIZED_ERROR("A0300", "访问权限异常"),
ACCESS_UNAUTHORIZED("A0301", "访问未授权");
```

**认证类都以 `A0` 开头**，`-1` 只表示"通用业务失败"。所以前端改成：

```js
const isAuthError = (code) => typeof code === 'string' && code.startsWith('A0')

if (data.code === '200')  return data.data
if (isAuthError(data.code)) { 清 token + 跳登录 }   // 只有认证失败才踢人
// 其他一律把后端给的真实原因抛出去
ElMessage.error(data.message || '操作失败')
```

修完再点知识库，正常显示空列表。

## 5.5 顺带查出的三个连带问题

**① 字段名写错了，用户从来没看到过真实错误。**

```js
ElMessage.error(data.msg || '登录过期')   // 后端返回的字段叫 message，不是 msg
```

`data.msg` 永远是 `undefined`，所以**不管什么错误，用户看到的永远是那句兜底的"登录过期"**。这个 bug 藏得很深 —— 因为它"看起来能用"。

**② 真正的 token 过期，反而从来没触发过跳转，甚至拿不到任何提示。**

后端认证失败返回的是 HTTP 401 / 403，axios 对 4xx 会走 **error 分支**，而原来的 error 分支只写了 `Promise.reject(error)` —— **什么都没做**。

所以这个拦截器的实际行为是完全颠倒的：**该踢人的时候不踢，不该踢人的时候乱踢。**

顺着这条线往下查，还挖出一个**后端的隐藏 bug**：

我在过滤器里写了好几个分支 —— `TOKEN_INVALID`（无效）、`TOKEN_EXPIRED`（过期）、`TOKEN_BLOCKED`（黑名单），每个配了不同的提示语。但实测发现，**token 过期或被篡改时返回的是「HTTP 403 + 空响应体」**，一个字节都没有。

根因是 `validateToken()` 在"格式非法 / 签名不对 / 已过期"时是**抛异常**，而不是返回一个"无效"的结果：

```java
JwtTokenUtil.TokenVerificationResult validationResult = JwtTokenUtil.validateToken(token);
// ↑ verifyToken() 在这里直接 throw，异常穿透整个过滤器链，
//   最后被 Spring Security 的 ExceptionTranslationFilter 兜成 403 + 空 body
```

**也就是说，我精心写的那几个分支全是死代码，从来没执行过。** 用 try-catch 兜住异常之后：

```
不带 token     → 401  {"code":"A0301","message":"访问未授权"}
乱造的 token   → 401  {"code":"A0230","message":"token无效"}
篡改一个字符   → 401  {"code":"A0230","message":"token无效"}
登出后再访问   → 401  {"code":"A0230","message":"token已加入黑名单"}
```

**教训：异常和"无效的返回值"是两条不同的路径，只处理其中一条等于没处理。**
我写代码时想的是"验证失败会返回一个 invalid 的结果"，但实际实现是"验证失败会抛异常" —— 我对自己代码的行为假设错了，而且这条路径一直没被测过。

**③ 兜底分支会返回错误的数据结构。**

```js
if (data.code === '200') { return data.data }
else if (data.code === '-1') { ...跳转... }
// ← 其他所有 code 直接落下来：return response（整个 axios 响应，不是 data.data）
```

调用方写的是 `getList().then(res => res.records)`，拿到一个 axios response 对象，`res.records` 是 `undefined`，**页面静默地什么都不显示**。任何新增的错误码都会掉进这个坑。

## 5.6 为什么我把它当成一个"设计"问题而不是"改个 if"

因为这四条修改，本质上都在回答同一个问题：**边界上的信息，应该由谁负责表达得足够清楚。**

- 错误码 → 由**后端**负责用不同编码区分语义，不能全塞进一个 `-1`；
- 字段名 → 前后端的**契约**必须是同一个词，`msg` 和 `message` 差一个字母就是永久性 bug；
- 分层处理 → 认证失败是**全局**行为（登出 + 跳转），业务失败是**局部**行为（提示一下、页面该怎么显示还怎么显示），两者不该走同一条路。

**一句话总结：接口的返回值是前后端的契约。契约里"含义模糊"的地方，就是一定会长出 bug 的地方 —— 而且它会以最难看的方式长出来：把业务失败误判成身份失效。**

**【追问】怎么避免这类问题？**

> 三个层面：
> 1. **错误码要有分段**：认证一段、参数一段、业务一段、系统一段。我后端的 `ResultCode` 其实已经这么分了（`A0xxx` / `4xxx` / `5xxx` / `6xxx`），问题出在前端没用上。
> 2. **HTTP 状态码和业务码各司其职**：认证失败该配 HTTP 401（我后端就是这么做的），不要全用 200 包业务码 —— 否则 HTTP 层的信息完全浪费了，前端只能去猜 body。
> 3. **联调前先对一遍契约**：字段名、错误码枚举、空数据的返回形态（空数组还是 null），这三个是最容易出问题的地方。

# 通用追问

**【追问】这个项目你印象最深的一个 bug？**

**首选讲"FC 假成功"那个（模块三 坑 6）。**

理由是它的根因和表象隔了三层：表象像"模型幻觉"，第一层是"工具没执行"，第二层是"Spring AI 的参数转换抛异常"，第三层才是"模型传了字符串 `"null"`"。
**只看前两层，你会去改提示词 —— 那是在给一个根本没坏的东西打补丁。** 而真正的定位手段是"先看日志定位到哪一行，再 `javap` 反编译确认那一行在干什么"。

而且它的失败方式最值得说：**不是报错、不是白屏，是用户以为记上了、其实什么都没有的假成功。** 这在业务系统里比崩溃危险得多。

**备选一：SSE 流完了却报 network error（模块二 2.2）。**
它让我第一次理解到 **"Servlet 异步派发 = 一次请求被处理两遍"**，以及 Spring Security 上下文为什么会在第二遍丢失。
**内容全对但连接异常关闭** —— 这个现象本身就指向"问题不在业务逻辑，而在请求生命周期管理"。

**备选二：点知识库被踢回登录页（模块五）。**
好处是**排查过程有完整的反转** —— 从"是不是权限配错了"一路挖到"错误码设计有问题"，结论一句话就能说清。

**对应的还有两个可以接着讲的**：

- **坑 7（模型记着记着就不动手了）** —— 同一个 FC 模块里更深的一层：
  **工具调用在对话历史里不留痕，模型学到的示范就变成"记录成功不用调工具"。**
  这个故事里还有一条我踩过的危险弯路：`tool_choice=required` 会在 Spring AI 的自动工具循环里**反复生效**，导致无限循环调用工具。
- **番外（我的调试工具骗了我三次）** —— 证明的是"我会怀疑自己的结论，而不是只怀疑代码"。
**【追问】这个项目有什么不足？**

（**别答"没有"**，也别把一个真缺陷说成"不足"。挑这三个说，都是有技术含量、且你已经有解决思路的）

三个，都有明确的解法，只是我按性价比排了优先级：

**一、流断了的容错。** 现在落库挂在"流正常结束"上，模型超时或网络中断会让这一轮彻底丢失（用户消息都不落库）。修法是把落库拆成两段：流开始时存用户消息并标记"进行中"，结束后补 AI 回复并置为"完成"，失败则标记"未完成"且不进上下文窗口。

**二、内容追加有丢失更新的窗口。** 同一天两笔并发写入时，两边都读到旧值、各自拼接、后写的覆盖前写的。生产里我会用 `SELECT ... FOR UPDATE` 加行锁，或者加乐观锁版本号。demo 阶段我判断不值得，但我知道它在哪。

**三、token 存 localStorage 有 XSS 风险。** 上线会换成 `HttpOnly + Secure + SameSite` 的 Cookie，代价是要处理 CSRF 和跨域。

**【追问】如果让你重做，你会改什么？**

**把"确定性逻辑"和"模型逻辑"的边界在架构上划清楚。**
这个项目里我是踩了坑之后才意识到：模型该负责的是**理解和生成**，不该负责**判断和决策**。
如果重做，我会在写工具的第一天就把这个边界定下来 —— **凡是"判错就不可逆"的动作（写、删、覆盖），决策权必须留在服务端代码里；模型只提供内容。**
现在这条是我通过 5 个坑换来的，比重做一次更值。

**【追问】你的 Redis 用了哪些数据结构？**

三种，都是"按业务动作选语义最贴合的那个"：

- **String**：token 黑名单（`SET key 1 EX 剩余秒数`）—— 只需要"存在/不存在"，String 最省。
- **List**：对话上下文（`RPUSH` + `LTRIM` + `LRANGE`）—— 天然匹配"只有尾部才有意义"。
- **String（JSON）**：文章缓存 —— 一整个对象的读写，不存在局部更新。

**【追问】MySQL 这边你做了什么优化？**

三个：

1. **唯一联合索引 `(user_id, diary_date)`** 在数据库层保证"一天一篇"，即使应用层出 bug 也插不出第二条。**这是我理解唯一索引的方式：它不是查询优化，它是业务规则的兜底。**
2. **冗余字段 + 原子自增**：会话表上冗余了 `last_message_content`（截 200 字）、`message_count`、`last_message_time`，让列表页不用 JOIN 消息表。计数用 `message_count = message_count + 1` 在数据库层自增，避免读-改-写丢更新。
3. **批量查用户避免 N+1**：日记列表页用 `selectBatchIds` 一次性把这一页涉及的用户捞出来，而不是循环里逐个查。

**【追问】`@Transactional` 你用在哪？**

落在"一轮对话落库"上 —— 用户消息和 AI 回复必须在一个事务里，否则会出现"消息存进去了、会话的计数没更新"的脏数据。

这里我踩过一个坑：**`@Transactional` 加在私有方法上、或者被同类内部直接调用，是不生效的** —— 因为它靠 Spring AOP 代理，自调用不经过代理。必须加在 public 入口方法上，或者从外部 Bean 调用。

**【追问】你怎么保证这些功能是对的？**

分两层验证，**因为这两层验证的东西不一样**：

- **端到端探针**（`tools/` 下 7 个：`chat-probe` / `diary-probe` / `article-probe` / `fc-probe` / `fc-overwrite-probe` / `fc-reliability-probe` / `date-probe`）—— 用 Node 直接打 HTTP 接口，看**真实链路**跑出来什么样。SSE 那个 bug 就是靠把 chunk 一个个打出来才定位的。
- **确定性测试**（`src/test/` 下的 `EmotionDiaryAppendTests`，7 个用例）—— 直接打 Service 和 Tool，**不掺模型的运气**。

为什么必须分开：AI 相关的功能，**模型的行为是概率性的**（同一句话有时记、有时不记；有时传片段、有时传全文）。拿它当测试输入，只会得到 flaky 的用例。
所以我的分工是：**端到端探针观测"模型的表现"，单元测试守护"我的逻辑"。** 模型哪天抽风，测试照样绿；我的逻辑写错了，测试立刻红。

两个细节值得说：

**一是这个测试第一次跑就挂了一个用例** —— 是我自己的断言写错了，我以为正文以"早上"开头，其实前面有时间戳。**测试第一次就抓到了我自己的错。**

**二是它的第一版写过一次很糟糕的设计。** 当时为了省事，测试直接用了 demo 账号（userId=10），并且在 `@BeforeEach/@AfterEach` 里清"当天"的日记 —— 结果它把 demo 账号那天的真实数据删掉了，我后来查一个问题时才发现"数据怎么没了"。

改法是从结构上隔离：**测试自己建一个独立账号**（`autotest_diary`），只清自己的数据，跟任何真实数据都不共享主键空间。

**"测试碰生产数据"不是靠小心就能避免的，得靠结构。** 这件事对我是个教训 —— 我一开始觉得"反正只是 demo 数据"，但数据就是数据，删了就是删了。

# 我的弱项（先说在前，别等被问）

**我对"高并发"没有实战经验。**
这个项目是单机跑、单用户测，我调的 Redis、MySQL 参数都是默认值，没做过压测，也没处理过真实的分布式一致性问题。

但**上面这些取舍我是想清楚了的** —— 比如为什么缓存可以接受不一致、为什么黑名单必须 fail-closed、为什么追加要有丢失更新的窗口。这些判断的依据是**业务对它的要求**，不是"大家都这么写"。

我知道自己缺的是**规模化的经验**，这个得靠真实项目补。

| 项 | 值 |
|---|---|
| 上下文窗口 | **20 条消息 = 10 轮对话** |
| 对话缓存 TTL | **30 分钟**，每次写入续期 |
| 对话缓存 key | `chat:history:{sessionId}` |
| 黑名单 key | `jwt:blacklist:{sha256(token)}` |
| 黑名单 TTL | **token 的剩余寿命**（不是固定值） |
| 文章缓存 | `knowledge:article:{id}`，TTL 30 分钟 |
| JWT | HS256，有效期 **24 小时** |
| Redis 客户端 | Lettuce，连接池 max-active 8，超时 3s |
| 认证类错误码 | **`A0` 开头**（A0230 token 无效/过期/黑名单、A0231 禁止访问、A0300 权限异常、A0301 未授权） |
| 通用业务失败码 | `-1`（`Result.error()` 的默认值，**不要拿它判断身份是否失效**） |
| 技术版本 | Spring Boot 3.4.6 / Java 17 / Spring AI 1.0.1 / MyBatis-Plus 3.5.12 / java-jwt 4.5.0 / hutool 5.8.25 |

**八条必须能脱口而出的话：**

1. **同一个 Redis，两种策略**：黑名单 fail-closed 是防线，对话缓存 fail-open 是加速器。
2. **模型负责理解，代码负责决策**：判错就不可逆的事，不能交给概率性的组件。
3. **SSE 流完报错**：Servlet 异步派发 = 请求被处理两遍，SecurityContext 第二遍丢了。
4. **窗口大小不是技术参数，是产品参数**：盲目扩大反而稀释注意力、白烧 token。
5. **一个错误码承载多种语义，调用方就只能猜**：`-1` 被当成"登录过期"，结果业务失败把用户的登录态清掉了。
6. **异常和"无效的返回值"是两条路径**：我写了 `TOKEN_INVALID` 分支，但实际实现是抛异常 —— 那条分支从来没被执行过。
7. **假成功比崩溃危险**：模型调了工具、Spring AI 在参数转换时抛异常、工具没执行 —— 但模型照样回"已经帮你记好了"。
8. **历史就是示范**：工具调用在对话历史里不留痕，模型学到的就是"记录成功不用调工具"，几轮之后它就开始只动嘴不动手。
